1. למה קיבלתי קטע שהשם בכלל לא מופיע בו? 1. Why did I get a chunk that does not contain the name?

כי החיפוש לא מסנן, הוא מדרג. הוא לא שואל "באילו קטעים מופיע השם?" אלא "מי 5 הקטעים הכי קרובים לשאלה?", ותמיד מחזיר 5, גם אם רק אחד מהם באמת רלוונטי. אין בקוד סף מינימלי של התאמה.

ואצלך זה בולט במיוחד: בכל המאגר יש רק 6 קטעים. כל עמוד קצר מ-800 תווים, אז כל עמוד הוא קטע אחד. לכן כל שאלה, לא משנה מה תשאלי, מחזירה 5 מתוך 6. כמעט הכול חוזר תמיד.

יש שני חיפושים שרצים במקביל, והם מתנהגים אחרת:

  • חיפוש וקטורי (לפי משמעות): קטע על משפחה מלודז' עם שנות לידה "קרוב" לשאלה על שנת לידה, גם בלי השם.
  • חיפוש BM25 (לפי מילים מדויקות): מחזיר את הרשימה שלו גם כשהציון של קטע הוא 0.

זה לא באג. הרעיון הוא להביא למודל קצת יותר מדי, ולתת לו הוראה לענות רק ממה שכתוב ולהתעלם מהשאר.

Because search does not filter, it ranks. It does not ask "which chunks contain the name?" but "which 5 chunks are closest to the question?", and it always returns 5, even when only one is really relevant. The code has no minimum-match threshold.

In your case this is extreme: the whole corpus is only 6 chunks. Every page is shorter than 800 characters, so every page is exactly one chunk. So any question at all returns 5 of the 6. Almost everything comes back every time.

Two searches run side by side, and they behave differently:

  • Vector search (by meaning): a chunk about a family from Lodz with birth years is "close" to a question about a birth year, even without the name.
  • BM25 search (by exact words): returns its list even when a chunk's score is 0.

This is not a bug. The idea is to bring the model slightly too much and instruct it to answer only from what is written and ignore the rest.

2. איך לדעת שתשובה באמת טובה? 2. How do I know an answer is really good?

תשובה שנשמעת בטוחה איננה הוכחה. יש שלושה מקומות שבהם דברים משתבשים, וכל אחד נבדק אחרת:

  1. התעתוק שגוי. המודל קרא את התמונה לא נכון. התשובה תצטט נאמנה טקסט שגוי.
    בדיקה: הלשונית "בדיקת תעתוק" בממשק, תמונה מול טקסט.
  2. האחזור פספס. הקטע הנכון לא הגיע למודל.
    בדיקה: לפתוח את "קטעים שאוחזרו" ולראות אם המסמך הנכון שם.
  3. המודל המציא. הקטע הנכון הגיע, אבל התשובה לא כתובה בו.
    בדיקה: למצוא בקטעים את המשפט המדויק שעליו התשובה נשענת. אין משפט כזה? התשובה לא אמינה.

שלוש בדיקות שכדאי לעשות עכשיו:

  • לשאול על משהו שלא קיים (כמו חיים שפירא). תשובה טובה: "לא נמצא במסמכים".
  • להריץ את ההערכה (הלשונית "הערכה", או הריצה בשורת הפקודה). יש שם 8 שאלות שהתשובה עליהן ידועה מראש.
  • להוסיף ל-eval_set.json שאלות משלך, כולל שאלות "מלכודת" בלי תשובה.

An answer that sounds confident is not evidence. Things go wrong in three places, and each is checked differently:

  1. The transcript is wrong. The model misread the image. The answer will faithfully quote wrong text.
    Check: the "בדיקת תעתוק" (transcript check) tab, image beside text.
  2. Retrieval missed. The right chunk never reached the model.
    Check: open "retrieved chunks" and see whether the right document is there.
  3. The model made it up. The right chunk arrived, but the answer is not written in it.
    Check: find the exact sentence in the chunks that the answer rests on. No such sentence? Do not trust the answer.

Three checks worth doing now:

  • Ask about something that does not exist (like Chaim Shapira). A good answer: "לא נמצא במסמכים".
  • Run the evaluation (the "הערכה" tab, or the command-line run). It has 8 questions with known answers.
  • Add your own questions to eval_set.json, including "trap" questions with no answer.

מה ההערכה מודדת, ומה לא What the evaluation measures, and what it does not

ההערכה מחזירה שני מספרים נפרדים, כדי לדעת איפה הבעיה:

  • אחזור: האם המסמך הנכון היה בין 5 הקטעים.
  • תשובה: האם המילה הצפויה מופיעה בתשובה.

שתי מגבלות שחשוב להכיר:

  • עם 6 קטעים ו-5 שחוזרים, ציון האחזור כמעט מובטח. הוא לא באמת בוחן את החיפוש. כדי לבחון אותו, שני בקוד את TOP_K = 5 ל-TOP_K = 2 והריצי שוב.
  • בדיקת התשובה היא רק "האם המחרוזת מופיעה". אם התשובה הצפויה היא 1925 והמודל כתב "לא 1925 אלא 1926", זה ייספר כהצלחה.

The evaluation returns two separate numbers, so you know where the problem is:

  • Retrieval: was the right document among the 5 chunks.
  • Answer: does the expected word appear in the answer.

Two limits worth knowing:

  • With 6 chunks and 5 returned, the retrieval score is almost guaranteed. It does not really test the search. To test it, change TOP_K = 5 to TOP_K = 2 in the code and run again.
  • The answer check is only "does the string appear". If the expected answer is 1925 and the model wrote "not 1925 but 1926", it counts as a success.
rows.append({
    "question": case["question"],
    "retrieved": any(h.metadata["source"] == case["source"] for h in hits),
    "answered": case["expected"] in reply,
    "reply": reply,
})

Transcription and answering use the same model, but they are two entirely different calls with different prompts. The embeddings model is a different kind: it writes no text, it only turns text into numbers. The names are set at the top of rag_skeleton.py and can be swapped without touching the code, through environment variables:

שלב 1: תעתוקStep 1: Transcription

התמונה מקודדת ל-base64 ונשלחת יחד עם ההוראות בהודעה אחת. ההוראות אומרות: לא לתרגם, לא לתקן כתיב, ולסמן מילים לא קריאות.

The image is base64-encoded and sent with the prompt in one message. The prompt says: do not translate, do not fix spelling, and mark unreadable words.

def transcribe(image, mime, vision_llm, budget):
    budget.spend("תעתוק עמוד")
    b64 = base64.b64encode(image).decode()
    msg = HumanMessage(content=[
        {"type": "text", "text": TRANSCRIBE_PROMPT},
        {"type": "image_url", "image_url": {"url": f"data:{mime};base64,{b64}"}},
    ])
    return vision_llm.invoke([msg]).text

לפני כל קריאה בודקים אם העמוד כבר תועתק. אם כן, קוראים מהדיסק ולא משלמים שוב:

Before each call the code checks whether the page was already transcribed. If so, it reads from disk and does not pay again:

def cache_path(path, page_no):

שלב 2: ChunkingStep 2: Chunking

הטקסט נחתך לקטעים של עד 800 תווים, עם חפיפה של 150 תווים בין קטע לקטע, כדי שמשפט שנחתך באמצע יופיע שלם לפחות באחד מהם. החיתוך מעדיף פסקה, אחר כך שורה, אחר כך משפט.

The text is cut into chunks of up to 800 characters, with a 150-character overlap between neighbors, so a sentence cut in the middle appears whole in at least one. The cut prefers a paragraph break, then a line, then a sentence.

def split(docs):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=800, chunk_overlap=150, separators=["\n\n", "\n", ". ", " "],
    )
    chunks = splitter.split_documents(docs)
    for i, c in enumerate(chunks):
        c.metadata["chunk_id"] = i
    return chunks

שלב 3: אינדקסStep 3: Index

נבנים שני אינדקסים על אותם קטעים. הווקטורי תופס משמעות ("נגר" קרוב ל-"Tischler"). ה-BM25 תופס מילים מדויקות, שזה חשוב לשמות ולמספרים.

Two indexes are built over the same chunks. The vector one captures meaning ("נגר" is close to "Tischler", both carpenter). BM25 captures exact words, which matters for names and numbers.

class HybridRetriever:
    def __init__(self, chunks, embeddings):
        self.vector = InMemoryVectorStore.from_documents(chunks, embeddings)
        self.bm25 = BM25Retriever.from_documents(chunks, k=TOP_K * 2, preprocess_func=tokenize)

האינדקס עצמו לא נשמר לדיסק. ה-embedding של כל קטע נשמר בנפרד ב-embcache, לפי טביעת אצבע של הטקסט, ולכן בנייה מחדש שולחת ל-API רק קטעים חדשים או קטעים שהשתנו. כשאין שום דבר חדש, האתר בונה את האינדקס לבד בפתיחה, בלי קריאת API.

The index itself is not saved to disk. Each chunk's embedding is saved separately in embcache, keyed by a hash of its text, so a rebuild sends only new or changed chunks to the API. When nothing is new, the site builds the index on its own at startup with no API call.

שלב 4: אחזור היברידי ומיזוג RRFStep 4: Hybrid retrieval and RRF fusion

def search(self, query, k=TOP_K):                          # TOP_K = 5
    ranked_lists = [
        self.vector.similarity_search(query, k=k * 2),      # up to 10 by meaning
        self.bm25.invoke(query),                            # up to 10 by words
    ]
    scores, by_id = {}, {}
    for results in ranked_lists:
        for rank, doc in enumerate(results):
            cid = doc.metadata["chunk_id"]
            scores[cid] = scores.get(cid, 0) + 1 / (60 + rank)
            by_id[cid] = doc
    best = sorted(scores, key=scores.get, reverse=True)[:k]
    return [by_id[cid] for cid in best]

RRF (Reciprocal Rank Fusion) ממזג שתי רשימות בלי להשוות ציונים, רק לפי מקום ברשימה. כל קטע מקבל 1/(60+מקום) מכל רשימה, והמקום הראשון הוא 0.

  • קטע שראשון בשתי הרשימות: 1/60 + 1/60 = 0.0333
  • קטע שאחרון (שישי) בשתיהן: 1/65 + 1/65 = 0.0308

כאן רואים שוב את התשובה לשאלה 1: כל רשימה מבקשת עד 10 קטעים, ויש רק 6, אז כל ששת הקטעים מקבלים ציון. 5 הראשונים חוזרים, ורק אחד נשאר בחוץ.

RRF (Reciprocal Rank Fusion) merges two lists without comparing scores, only by position. Each chunk gets 1/(60+rank) from each list, and first place is rank 0.

  • A chunk first in both lists: 1/60 + 1/60 = 0.0333
  • A chunk last (sixth) in both: 1/65 + 1/65 = 0.0308

Here is the answer to question 1 again: each list asks for up to 10 chunks and there are only 6, so all six get a score. The top 5 are returned and only one is left out.

שלב 5: תשובהStep 5: Answer

5 הקטעים מודבקים לתוך ההוראות, כל אחד עם כותרת של קובץ ועמוד, והשאלה בסוף. ההוראות (בעברית) אומרות: לענות רק מהקטעים, לציין מקור אחרי כל עובדה, לכתוב "לא נמצא במסמכים" אם אין תשובה, ולא לנחש שמות, תאריכים או מספרים.

The 5 chunks are pasted into the prompt, each with a file-and-page header, and the question comes last. The prompt (in Hebrew) says: answer only from the chunks, cite the source after every fact, write "לא נמצא במסמכים" if there is no answer, and do not guess names, dates or numbers.

def answer(question, retriever, llm, budget):
    hits = retriever.search(question)
    context = "\n\n".join(
        f"[{d.metadata['source']}, עמוד {d.metadata['page']}]\n{d.page_content}" for d in hits
    )
    budget.spend("תשובה לשאלה")
    reply = llm.invoke(ANSWER_PROMPT.format(context=context, question=question)).text
    return reply, hits

המודל לא "זוכר" את המסמכים ולא אומן עליהם. הוא רואה רק את 5 הקטעים שנשלחו אליו באותה קריאה. זו כל המשמעות של RAG: מחפשים קודם, ואז נותנים למודל לקרוא.

The model does not "remember" the documents and was not trained on them. It sees only the 5 chunks sent in that call. That is the whole meaning of RAG: search first, then let the model read.

7. האם יש Vector DB? 7. Is there a vector database?

לא. אין שרת מסד נתונים בפרויקט. הקוד משתמש ב-InMemoryVectorStore של LangChain: רשימה של וקטורים בזיכרון של Python. בחיפוש הוא משווה את וקטור השאלה לכל אחד מהם (דמיון קוסינוס) ומחזיר את הקרובים ביותר. כדי לא לחשב שוב בכל הפעלה, הרשימה נשמרת לקובץ JSON ונטענת ממנו.

ל-6 קטעים, וגם לכמה אלפים, זה מספיק לגמרי.

Chroma מותקן אצלך אבל לא בשימוש. ברשימת החבילות של המורה יש langchain_chroma, שהוא Vector DB אמיתי שנשמר לדיסק. סביר שתשתמשו בו בהמשך הקורס. ההחלפה קטנה, כי שניהם מציעים את אותן פעולות:

No. There is no database server in this project. The code uses LangChain's InMemoryVectorStore: a list of vectors in Python's memory. On search it compares the question's vector with each of them (cosine similarity) and returns the closest. To avoid recomputing on every start, the list is saved to a JSON file and loaded from it.

For 6 chunks, and for a few thousand, this is entirely enough.

Chroma is installed on your machine but not used. Your teacher's package list includes langchain_chroma, a real vector database that persists to disk. You will likely use it later in the course. The swap is small, because both offer the same operations:

# today
from langchain_core.vectorstores import InMemoryVectorStore
store = InMemoryVectorStore.from_documents(chunks, embeddings)

# with Chroma (not in your code today)
from langchain_chroma import Chroma
store = Chroma.from_documents(chunks, embeddings, persist_directory="chroma_db")

מתי כן צריך מסד נתונים אמיתי: כשיש מאות אלפי קטעים, כשרוצים להוסיף מסמך בלי לבנות הכול מחדש, או כשרוצים לסנן לפי מטא-דאטה (למשל רק מסמכים משנת 1941).

When a real database is needed: with hundreds of thousands of chunks, when you want to add a document without rebuilding everything, or when you want to filter by metadata (for example only documents from 1941).

8. הגנות עלות 8. Cost guards

כל קריאת API עוברת דרך מונה אחד. מעבר לתקרה, התוכנית נעצרת עם הודעה.

Every API call goes through one counter. Past the limit, the program stops with a message.

class Budget:
    def spend(self, what):
        if self.used >= self.limit:        # limit = 60 calls per run
            raise BudgetExceeded(...)
        self.used += 1
